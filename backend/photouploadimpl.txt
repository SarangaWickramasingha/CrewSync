Photo Upload & Delete Implementation Notes (UPDATED)
=====================================================

Scope: Service Provider can add project photos to a review they received and
delete them. Frontend refactored into reusable components (DRY). This file is
the reference for BOTH sides; backend sections give exact request/response and
permission rules.

=========================================================================
BACKEND — CrewSync-backend/backend
=========================================================================

1) FILES INVOLVED
   - controllers/ProviderController.php  (all logic)
   - routes/provider.php                 (function wrappers)
   - index.php                           (router / URI mapping)
   - uploads/review_photos/              (stored files)
   - DB table: review_photos (review_id, photo_id, file_path)

2) ENDPOINTS (index.php)
   GET    /api/provider/reviews/all                -> getAllReviews        (line 256)
   POST   /api/reviews/{review_id}/photos          -> uploadProviderReviewPhotos (lines 260-262)
   DELETE /api/review-photos/{photo_id}            -> deleteProviderReviewPhoto (lines 264-266)

   routes/provider.php wrappers:
   - uploadProviderReviewPhotos($reviewId)  (line 40)
   - deleteProviderReviewPhoto($photoId)    (line 44)

3) CONTROLLER METHODS — controllers/ProviderController.php

   a) getUploadsBaseUrl() (line 21)
      Returns "{$scheme}://{$host}/CrewSync-backend/backend/uploads/".
      Every photo URL returned to the frontend = base + file_path.

   b) getAllReviews() (lines 484-529)
      - Role: service_provider (requireRole)
      - Resolves provider_id from logged-in user
      - Per review, loads: SELECT photo_id, file_path FROM review_photos WHERE review_id = ?
      - Response shape per review:
          "photos": [ { "photo_id": int, "url": "<base>/review_photos/<file>" } ]
      - Also used (public) getPublicProfile() lines 574-585 for guest view,
        but that one returns photos as plain URL strings only.

   c) uploadReviewPhotos($reviewId) (lines 631-690)
      - Role: service_provider
      - Permission: review must exist AND r.provider_id = caller's provider_id
        (SELECT ... WHERE review_id = ? AND provider_id = ?) else 403.
      - Input: multipart/form-data, field key = "photos" (array of files)
        (frontend also sends "images[]" but backend IGNORES it)
      - Validation per file:
          * error must be UPLOAD_ERR_OK
          * MIME (mime_content_type) in [image/jpeg, image/png, image/webp, image/gif]
          * size <= 5MB (5 * 1024 * 1024)
        Invalid/skipped files are silently dropped.
      - Filename: review_{reviewId}_{time()}_{bin2hex(random_bytes(4))}.{ext}
        (ext sanitized to [a-zA-Z0-9])
      - Store: move_uploaded_file -> uploads/review_photos/<filename>
      - DB: INSERT INTO review_photos (review_id, file_path) VALUES (?, "review_photos/<filename>")
      - Response: { "success": true, "photos": [ { "photo_id": int, "url": "<base>/review_photos/<file>" } ] }

   d) deleteReviewPhoto($photoId) (lines 693-721)
      - Role: service_provider
      - Permission: photo must belong to a review owned by caller:
          SELECT rp.file_path FROM review_photos rp
          JOIN reviews r ON r.review_id = rp.review_id
          WHERE rp.photo_id = ? AND r.provider_id = ?
        else 404 "Photo not found".
      - Deletes physical file: $filePath = uploads/<file_path>; unlink() if exists
      - DB: DELETE FROM review_photos WHERE photo_id = ?
      - Response: { "success": true }

4) STORAGE / DB
   - Dir: backend/uploads/review_photos/
   - Table review_photos created in SQL dump/seeds (NOT in PHP code):
       review_id  (FK -> reviews.review_id)
       photo_id   (PK auto-increment)
       file_path  (VARCHAR; value = "review_photos/<filename>")
   - No record of owner on review_photos itself; ownership derives from the
     parent review's provider_id.

CONTRACT SUMMARY (for backend devs)
=========================================================================
- Auth: bearer token; role service_provider on all three endpoints.
- Ownership: photo ops require the review's provider_id == logged-in provider.
  403 for wrong provider on upload; 404 on delete if not found/unauthorized.
- Upload: POST multipart, files under "photos[]", max 5MB each, MIME allowed
  jpeg/png/webp/gif. Success returns per-file photo_id + absolute URL.
- Delete: DELETE by photo_id; unlinks file then removes DB row.
- Serving files: PHP/htdocs serves uploads/ directly (no auth on static files).
- Table review_photos: photos carry no owner column; use parent review for auth.

3. R2 SPECIFICS
----------------------------------------------------------------------
- R2 exposes an S3-compatible API at https://<ACCOUNT_ID>.r2.cloudflarestorage.com
  (S3 SDKs talk to it directly). SigV4 signing supported -> works with the
  currently installed aws/aws-sdk-php 3.337.0 (pinned for PHP 8.0).
- Credentials: R2 Access Key ID + Secret Access Key (created in Cloudflare
  dashboard > R2 > Manage R2 API Tokens), NOT the current invalid AWS keys.
- Target bucket (provided by user, Sep 20 2026):
      Bucket name : crewsync          (location: Asia-Pacific APAC)
      Account id  : b125684ad4aadcc257ae31677b02376e
      S3 API      : https://b125684ad4aadcc257ae31677b02376e.r2.cloudflarestorage.com/crewsync
                    (endpoint = https://b125684ad4aadcc257ae31677b02376e.r2.cloudflarestorage.com,
                     final URL = endpoint + "/crewsync")
- Region: use "auto".
- Public access decision (GET URLs returned to the frontend):
    Option A — PRIVATE bucket + PRESIGNED GET URLs (recommended, zero dashboard
               setup): backend generates $s3->createPresignedUrl(GetObject cmd,
               expiry) per photo. Pros: bucket stays private. Cons: URLs expire
               (set BUCKET_URL_EXPIRY_SECONDS, e.g. 3600; frontend must re-fetch
               the review list to get fresh URLs — which it already does).
    Option B — PUBLIC bucket + custom domain (or *.r2.dev): permanent URLs
               https://<pub-host>/review_photos/<file>. Pros: cacheable, permanent.
               Cons: bucket must be made public in the Cloudflare dashboard; set
               R2_PUBLIC_URL so backend can build URLs.
  Decision recorded: implement Option A first (works out of the box); the code
  will branch on R2_PUBLIC_URL being set, so Option B is a config change later.
